# matmul_v2 H100 reproduction notes

## What is reproduced

- Entry point: `custom_kernel(data)` with `data = (a, b, c)`.
- Main H100 top1 idea: do not hand-write a CUDA/Triton GEMM. Let PyTorch/cuBLAS pick the matmul implementation by returning `a @ b`.
- Import-time environment setup: set `CUBLAS_WORKSPACE_CONFIG=:4096:8`, matching the insight that the H100 path relies on cuBLAS/PyTorch while staying compatible with the deterministic reference check.
- The function intentionally does not write `c` on the default path. The official checker compares the returned tensor against `a @ b`, and the reference also returns a fresh matmul result.

## Simplifications

- No cuBLASLt direct calls, no heuristic search, and no Triton kernel. Those ideas were relevant to other runners in the insight document, but the H100 top1 approach was the plain PyTorch/cuBLAS path.
- No shape-specialized dispatch for `(4096, 5120, 4096)` or other benchmark cases, because the H100 idea is to avoid wrapping the library path.
- A small optional fallback exists behind `GPUMODE_MATMUL_V2_FORCE_OUT=1`; it computes `torch.mm(a, b, out=c)` when `c` is compatible. This is meant for local integration/debugging, not for the H100 leaderboard path.

## Validation requirements

- Official validation needs a CUDA GPU, ideally the H100 runner used by the benchmark, with PyTorch and cuBLAS available.
- Inputs are expected to be CUDA, contiguous, row-major `float16` tensors with dimensions that are multiples of 16, as generated by the task harness.
- This local machine reports `torch.cuda.is_available() == False`, so I could only run import/CPU smoke checks here, not the official evaluator or GPU timing.
